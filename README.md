# Progress-Driven SDLC

**Short conversations. Clear progress. Human control.**

Start with you and one coding agent. Add ChatGPT Web or teammates when useful: you decide and accept; agents investigate, build, and verify. Specialist review still applies when risk or your organization requires it.

<a id="use-the-workflow"></a>

**Plan → Approve → Build → Verify → Accept**

## Use in your project

A clone is a source, not an initialized application. Follow the [reusable file map and neutral initialization](docs/ops/adopt-framework.md#reusable-map-and-neutral-initialization); do not copy this repository wholesale or inherit its maintenance approvals. Existing product files and active work stay intact.

Open your coding agent in the intended target and submit:

```text
Adopt https://github.com/edwardansberg/progress-driven-sdlc in this project.
Inspect the intended directory, Git boundary, instructions, and existing work.
Acquire a separate source snapshot, pin its full commit, and read
docs/ops/adopt-framework.md and its required references at that revision.
If source or guide is unavailable, stop without target writes.
I authorize a written plan and nonconflicting local documentation setup only.
Use the guide’s explicit reusable map; initialize state from this target,
not upstream memory. Preserve product files, active work, and Git state.
Ask before policy replacement, conflicting paths, or displacing work.
Do not initialize Git, commit, push, install software, or enable automation.
Verify and stop for my validation. Keep the briefing short.
```

## Develop this framework

Maintainers use topic/development branches and reviewed PRs; publication and merge require their named permissions. No direct main pushes. This upstream delivery rule does not require PRs for every solo adopting project. Pending development is not an accepted release.
